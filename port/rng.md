# The port contract

*`port/` holds the things a second implementation of Landnám's simulation must
agree with this one about. Nothing here is loaded by the game — it is a
contract, and the tests that enforce it run in this repo.*

There are two implementations. The web build is this repo; the Unreal build is
`landnam-ue`, which since 2026-08-10 has had `src/hex` and `src/rng` ported to
C++ (`Source/LandnamUE/LandnamHex.*`, `LandnamRng.*`) with a Blueprint surface
and an automation test, `LandnamParityTest.cpp`.

Every world, event and blow in this game comes out of one seeded generator.
`Math.random` is banned here and `FMath::Rand` is banned there, for the same
reason: the seed **is** the world. A port that is one bit off reproduces
nothing — and passes its own test suite the whole time, because a
self-consistent generator is still self-consistent when it is wrong.

## Who owns what

| file | what it is |
| --- | --- |
| `port/golden.json` | the shared contract. Vectors for hex and RNG, generated from `src/`. **This repo owns it**; `landnam-ue` consumes a copy at `Content/Data/golden.json`. |
| `port/rng-fixture.json` | this repo's own RNG tripwire — the helper edges (`int(5,5)`, `int(0,999999)`, `pick`, `roll(1,20)`) the shared file does not carry. |
| `test/goldenport.test.ts` | recomputes every vector in `golden.json` from live `src/`, and fails if any moved. |
| `test/rngport.test.ts` | the same job for `rng-fixture.json`. |

**Ownership is the whole point of this arrangement.** The vectors used to be
generated by a script that lived on one machine and was never committed here,
so the repo that owns the code the vectors describe had no idea the contract
existed. Change `src/rng.ts`, nobody regenerates, and the Unreal test goes on
passing against yesterday's expectations while the two builds quietly
disagree. A green parity test that can only see one side of the parity is
worse than no test, because it is reassuring.

### The workflow

1. Change something in `src/hex` or `src/rng`.
2. `npm test` fails, naming what moved. If you did not mean to change the
   generator, **stop** — that is a save-and-world-breaking change, not a test
   to update.
3. If it was deliberate, regenerate the vectors and copy `port/golden.json`
   into `landnam-ue` at `Content/Data/golden.json`.
4. Run `Landnam.Parity` in Unreal (Tools › Session Frontend › Automation).

Both sides move together or neither does.

## The algorithm, exactly

### 1. Hash the seed string — FNV-1a over UTF-16 code units

```js
let h = 0x811c9dc5;
for (let i = 0; i < text.length; i++) {
  h ^= text.charCodeAt(i);
  h = Math.imul(h, 0x01000193);
}
return h >>> 0;
```

**This is the single most likely place a port silently diverges.** Measured
rather than warned about — the same string hashed three ways:

| seed | UTF-16 units *(correct)* | UTF-8 bytes | code points |
| --- | --- | --- | --- |
| `landnam` | 4186577160 | 4186577160 | 4186577160 |
| `Þórr` | 1670707610 | 153305670 | 1670707610 |
| `😀` | 3409036472 | 866293256 | 105948959 |

Read the first row and then the rest. **Every ASCII seed agrees under all
three**, which is why this bug survives testing: the game's own seeds are
`raven-skerry-317` and `curve-0`, and they can never catch it. The Norse
seeds catch a UTF-8 port. And **only the emoji catches a code-point port** —
it is one code point and two code units.

`golden.json` carried no non-ASCII case at all until 2026-08-11; the six now
in `rng.hashString` are there for this reason and none of them is decoration.

`Math.imul(a, b)` is a 32-bit multiply returning a **signed** 32-bit result:
`(int32_t)((uint32_t)a * (uint32_t)b)`.

### 2. mulberry32

```js
let a = seed >>> 0;
function next() {
  a = (a + 0x6d2b79f5) | 0;
  let t = Math.imul(a ^ (a >>> 15), 1 | a);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}
```

Note carefully: `| 0` produces a **signed** 32-bit value, and `>>>` is an
**unsigned** shift applied to that value's unsigned reinterpretation. Doing
the whole thing in `uint32_t` with `>>` gives the same bits — which is what
`LandnamRng.cpp` does — but mixing the two in one expression is where a
hand-translation goes wrong. So is `(1u | a)` and `(61u | t)`: those are ORs
with the *current* value, not constants, and the fixture catches that slip on
the very first draw.

`next()` returns the raw uint32 divided by `2**32`, which is exact in a
double. `rng-fixture.json` stores the **uint32**, never a decimal, because a
decimal is somewhere two languages can print the same number differently.

### 3. Stream and derive names are built by string concatenation

```
stream(seed, name)   →  makeRng(`${seed}#${name}`)
rng.derive(label)    →  makeRng(`${seed}::${label}`)
```

The delimiters `#` and `::` are part of the contract, and so are the stream
names — `worldgen`, `party`, `events`, `combat`, `colony`, `saga`. **Renaming
a stream or changing a derive label silently changes every existing seed.**
Chains concatenate, so `makeRng('root').derive('a').derive('b')` is
`makeRng('root::a::b')`.

### 4. The helpers, and how many draws each consumes

| helper | definition | draws |
| --- | --- | --- |
| `next()` | as above | 1 |
| `int(min, max)` | `min + floor(next() * (max - min + 1))` — both ends inclusive | 1 |
| `float(min, max)` | `min + next() * (max - min)` | 1 |
| `chance(p)` | `next() < p` | 1 |
| `roll(count, sides)` | sum of `count` calls of `int(1, sides)` | `count` |
| `pick(items)` | `items[int(0, items.length - 1)]` | 1 |
| `shuffle(items)` | Fisher-Yates **descending**: `for i = len-1; i > 0; i--` swap `i` with `int(0, i)` | `len - 1` |
| `weighted(items, w)` | one draw: `next() * total`, then walk subtracting each `max(0, w)`, returning the first item that takes the running value below zero | 1 |

The draw COUNT matters as much as the value: a port whose `roll(2, 6)` takes
one draw instead of two stays in step for exactly one call, and every
subsequent number in that stream is different.

## Reading `golden.json`

Each stream section draws from its **own fresh generator** on that stream's
seed, then sequentially within itself. The parameters are not written down
anywhere in the file, so for the record — recovered by solving against the
vectors, since the generating script was never committed:

| section | recipe | count |
| --- | --- | --- |
| `nextRaw` | raw uint32 | 250 |
| `ints` | `int(1, 6)` | 60 |
| `wideInts` | `int(-50, 250)` | 40 |
| `rolls` | `roll(2, 6)` | 30 |
| `chances` | `chance(0.3)` | 40 |
| `floats` | `float(-2.5, 7.5)` | 20 |
| `shuffles` | `shuffle([0..9])` | 5 |
| `weighted` | `weighted` over the `weights` array | 40 |
| `derived` | `derive(label)`, 5 raw draws each | 3 |

`chance` was pinned by solving rather than guessing: across the six streams
the booleans admit only `p ∈ (0.297557, 0.302485]`, and 0.3 is the only round
number in it.

Two encoding notes for the hex section. Path costs for an **unreachable**
goal are stored as `-1`, because JSON cannot write `Infinity`; both sides skip
the cost comparison when `reachable` is false. And `hex.neighbors`'
`directionTo` probe list is the six neighbours, then `(q + 2, r)`, then the
hex itself — so both "not adjacent" answers are pinned.

The C++ implementation is `landnam-ue/Source/LandnamUE/LandnamRng.cpp`. A
standalone reference used to live here; it was deleted once the real port
existed, because a second implementation nobody runs is a second
implementation that rots.

## What is NOT pinned here, and should be

This locks the **generator** and the **hex library**. It does not lock what
the game asks them for — the order in which systems draw, and the derive
labels they use. Those are just as load-bearing: `worldgen` taking one extra
draw moves every hex after it.

That is Phase 7 item 1's job — run both implementations on the same seed and
the same action list, and diff the resulting `GameState`. This is the floor
under it: if the generators disagree, a state diff tells you nothing, because
everything disagrees.
